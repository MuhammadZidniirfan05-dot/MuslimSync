# MuslimSync agent instructions

## Read first

Read [PRD](docs/PRD.md), [architecture](docs/ARCHITECTURE.md), [API notes](docs/api-notes.md), and the assigned issue before working. PRD and architecture are the source of truth; explicit user decisions take precedence. Work only on the issue scope. Do not refactor unrelated code or overwrite user changes.

If acceptance criteria or source documents conflict, ask in the issue and stop the dependent work. Continue independent, authorized work. Never guess a product decision. The API notes distinguish verified evidence, proposals, and approved decisions.

## Approved choices and unresolved decisions

- Stack: SvelteKit 2.x, Svelte 5 runes only, `@sveltejs/adapter-static`; Vite is supplied by SvelteKit. Do not scaffold Alpine.js or another framework.
- Quran: EQuran.id v2 is the approved primary source for Arabic, Indonesian translation, and recitation per ayah/surah.
- Hadith: MyQuran v2 is approved as a replacement candidate for Gading. Translation rights and pagination remain unresolved; candidate approval is not publication clearance.
- Routing: the user approved SvelteKit file-based routing. Feature navigation stays within MuslimSync; external APIs provide data and media, not replacement destination pages.
- Do not silently activate Quran translation fallbacks. Location disclosure, prayer accuracy policy, Hijri method/holidays, BMKG region mapping, and hosting remain open in [API notes](docs/api-notes.md). Block only the issues that depend on those decisions.

## Svelte and architecture

- Before writing a component, read the relevant [Svelte documentation](https://svelte.dev/docs/svelte/overview) and [SvelteKit documentation](https://svelte.dev/docs/kit/introduction). Record relevant documentation links in the PR.
- At scaffolding, verify the newest stable Svelte 5.x, SvelteKit 2.x, compatible tooling, and Node LTS. Use `sv create`; pin direct dependency versions and commit the lockfile. Do not use SvelteKit 3 prereleases or assume this document supplies current package versions.
- Use `$state`, `$derived`, `$effect`, and `$props` as appropriate. No `export let`, reactive `$:` statements, or `writable` stores for new state. Shared rune state belongs in `.svelte.js` modules as specified by the architecture.
- Follow service → normalizer → internal model → UI. Keep network/data logic out of components. Services return `{ data, source, fetchedAt, stale }` or managed errors.
- Application `fetch` calls belong only in `src/lib/core/http.js`. Do not bypass this with another HTTP client in UI. API data is fetched on the client through services; no runtime SvelteKit server dependency with adapter-static.
- Native `<audio src>` and `<img src>` load media URLs supplied by the normalized model; they are not JSON fetch calls. Validate HTTPS URLs before use. Do not assume media CORS equals API CORS or introduce blob fetching outside the HTTP layer.
- Resolve hosting/routing decisions before implementing route fallbacks. Browser-only APIs must not execute during prerender/SSR. Keep components focused and dependencies minimal; justify every added dependency.

## External data, privacy, and reliability

- Never invent endpoints, schemas, edition IDs, region codes, licenses, or attribution requirements. Consult official documentation and test real requests before adding an adapter; update [API notes](docs/api-notes.md) with dates and limits of the evidence.
- Validate HTTP status and payload shape. Render external strings through escaped Svelte interpolation or `textContent`; never use `{@html}` or `innerHTML` with external data. Preserve the actual Quran/hadith text.
- No API keys/secrets in client code, public environment variables, URLs generated by UI, fixtures, logs, or PR bodies. A secret-requiring provider needs an approved proxy design.
- Do not transmit real user coordinates until the unresolved location policy is settled. Do not claim third-party services retain no request data.
- Follow architecture defaults: timeout 8 seconds, at most two GET retries with exponential backoff, stale-while-revalidate. Retry only suitable failures; respect `Retry-After` and do not retry permanent client errors blindly.
- Cache keys must distinguish source, location/date/timezone, method/adjustments, or edition as applicable. Local storage keys use `ms:` and a schema version. Respect provider storage restrictions over a generic TTL.
- Provide loading, error, empty, and stale/offline states where relevant. Do not substitute a different location, translation, prayer method, or provider silently.
- Preserve attribution and source metadata. Religious content and prayer-time logic require human review before merge. API success alone does not prove religious or timing accuracy.

## UI and language

- UI language: Indonesian. Code identifiers and code comments: English.
- Use the PRD design tokens, native CSS, mobile-first layouts, and self-hosted fonts. Do not introduce an unplanned CSS framework.
- Check keyboard operation, visible focus, labels, contrast, and 360px layouts. Arabic text requires `lang="ar"`, `dir="rtl"`, and suitable line-height. Avoid autoplay assumptions for recitation.

## Issue → PR workflow

- Planner: one issue should fit one focused PR, ideally fewer than 300 changed lines excluding generated files. Include context/PRD references, scope, exclusions, affected files, testable acceptance criteria, technical notes, dependencies, and Definition of Done.
- Do not mark an issue `agent:ready` until criteria, dependencies, and required human decisions are resolved. New template submissions are not automatically ready.
- Implementer: use `feat/<issue>-<slug>` (or `fix/` / `chore/` as appropriate), implement the criteria, and open a PR with `Closes #<number>` and the [PR template](.github/pull_request_template.md). Revise the same PR after review.
- Workflow is semi-manual initially. Do not add agent automation, merge, or deploy without authorization. The human makes the final merge decision.
- Editing this file, workflows, or secrets requires explicit human authorization under architecture §19. An issue explicitly approved by the human for those changes is sufficient; reference that authorization in the PR. Do not ask again for already authorized scope.
- [Label definitions](.github/labels.json) are a proposed GitHub label catalog, not an installed configuration. Create them in the target repository before using the templates. `milestone:*` labels do not create GitHub milestones. Repository settings, CODEOWNERS, and branch protection must be configured separately; their existence must not be claimed from these files.
- Apply only one current `agent:*` state per tracked item: `ready → in-progress → in-review → approved`, or `in-review → changes-requested → in-progress`. Update issue/PR states consistently and remove obsolete states. `needs-human` marks blocked decisions or escalation; do not leave an escalated issue ready.

## Validation and Definition of Done

- Run `npm run lint`, `npm test`, and `npm run build` before opening a review-ready code PR. Record actual commands, results, and environment. Do not claim checks passed if tooling is absent or commands did not run.
- Add meaningful tests for changed behavior: normalizers, countdown/date boundaries, qibla, cache, and error handling as relevant. Use deterministic fixtures/mocks; live API calls belong to integration verification, not ordinary unit CI.
- Run relevant Playwright smoke checks for UI/navigation/error changes and the established CI checks. Verify bundle/performance budgets where affected: initial JS <100 KB gzip; target LCP <2.5 seconds and Lighthouse categories ≥90 per PRD.
- Documentation-only or pre-scaffolding changes may report unavailable/not-applicable runtime checks with reasons. Validate their structure/content instead; this does not waive future application CI or allow false green results.
- Remove debugging `console.log` calls. Include manual reproduction steps and screenshots for UI changes. Explain any check that is not applicable, any new dependency, and remaining risks.

## Reviewer rubric and three-round limit

Verify all eight areas: acceptance criteria; service/model/UI and runes architecture; safe external rendering; loading/error/empty states; meaningful tests and green required CI; scope/dependencies; accessibility; readable, maintainable code.

Review the current diff and commit, not only the Implementer's summary. Return **APPROVE** or **REQUEST_CHANGES**. List blocking findings first, followed by suggestions. Each finding needs file, line, violated criterion/rule, evidence or reproduction, and the requested correction. Distinguish unverified claims from defects. Do not approve while required checks or blocking criteria remain unresolved.

Record `Round N/3` and the reviewed commit in every formal review. Initial review is round 1; revisions are rounds 2 and 3. If round 3 still needs changes, add `needs-human`, summarize remaining blockers and attempts, and stop the automated revision loop. A human chooses how to continue; do not reset the counter by opening a replacement PR.
